# Working merchant commerce applications

For a working single-merchant or multi-merchant commerce request, use `create_commerce_app` before visual styling. Set the required `mode` to `"single-merchant"` for one shared catalog or `"multi-merchant"` for separate merchant-owned shops. The number of SKUs does not select the merchant model. If the request does not establish the business model, clarify it before creating the document. The legacy `create_single_sku_shop_app` remains available for its original four-page single-SKU starter; it does not create the new merchant flows.

For `edition: "starter"` (the default), single-merchant creates storefront, buyer orders, login, product management and merchant orders. Management requires the verified `catalog-manager` role. Multi-merchant also creates a store directory and shop-opening flow. The platform first grants `merchant` through the identity service; the user then opens their own shop, with at most one shop per account. Product and merchant-order access uses server-side membership through the store's owner and ID. Never treat a route, hidden button, client filter, supplied store ID or browser role string as authorization. Do not give ordinary buyers or one merchant unrestricted access to another merchant's products or orders.

Reuse the existing public authentication contract. Choose `authentication: "local-keycloak"` only when the user selected the local OpenPencil Keycloak setup. Otherwise choose `"oidc"` with the user's public `issuer` and `client_id`; request missing public configuration without inventing it or requesting passwords, tokens or a client secret. Set `locale: "zh-CN"` for Chinese copy or `"en"` for English. Creation requires the installed, enabled, host-reviewed NestJS Backend Provider. If unavailable, use Settings → Plugins; never bypass provider checks with eval or handwritten plugin data.

Use a document without an existing Backend or authentication flow. Preserve existing pages and state. Older templates are not upgraded automatically: recreating in a new document and explicitly migrating an existing application are separate operations. Do not replace existing declarations, database schemas or unresolved saved attempts.

After creation, call `switch_page` with `shopPageId`, inspect every returned `exportPageId`, and style the existing pages. Preserve all controls, document/page states, bindings, events, resource queries, routes, authentication, commands and recovery actions. Export all returned pages together as React or Vue source. Do not replace functional pages with static product cards or decorative order controls.

In the starter edition, each order contains one SKU, with integer quantity 1–99 and server-calculated prices in integer minor units. Preserve stock checks and explicit confirmations. Checkout takes the template's declared parameters; never add client-calculated prices or stock changes. Stock additions use the reviewed command, not unrestricted inventory CRUD or an absolute stock replacement. Keep buyer-order and merchant-order projections separate and retain their server authorization. Public catalog fields must not contain private merchant or customer information.

Preserve browser recovery where authored: inspect the saved request after signing in again with the same account, explicitly retry its stored key and original parameters, then acknowledge only after checking the result. Never automatically resend, clear a saved key directly, or reuse current form values for a saved-request retry. Ordinary resource creation and metadata updates do not acquire the command's idempotency guarantees; check the resource list after a lost creation response before deciding to retry.

Report the selected mode, generated routes and source-export step. The tool changes only the document. It does not start services, provision shops or products in a database, grant roles, deploy, or prove real login or persistence. Follow the generated README for service setup. Starter editions do not include payments, multi-SKU carts, shipping, refunds or settlement records. Do not silently replace a starter document with the operations model.

## Operations edition

For payment/支付, multi-product cart/购物车, shipping/物流, refunds/退款 or settlement/分账 requests, set `edition: "operations"`. This creates a fresh extended application while retaining the selected single/multi merchant model. Both operations modes use merchant-owned stores, one store per account; single mode additionally permits only one store in the whole application. Set optional `commission_basis_points` to an integer from 0 to 10000 when specified; default 0. Do not guess a commission.

Preserve every returned page: saved server cart and quantity/removal controls, version-reviewed atomic checkout, purchases and store orders, simulated payment success/failure/unknown, manual carrier/tracking entry and buyer delivery confirmation, pre-shipment whole-order refund requests and operator approval/rejection, merchant settlement history and platform record confirmation. Payment simulation never collects money and is disabled in production. Unknown payment must remain pending for explicit recovery. Shipping is manual with no carrier API. Active refund requests are limited to paid, unshipped whole store orders; shipped or settled orders are rejected. Settlement uses server amounts and the default 7-day delay after delivery; recording a reference never means an automatic bank transfer.

The identity service grants `merchant` for store management and `commerce-operator` for platform refund/settlement decisions. Keep buyer, merchant and operator resource projections separate, including their `readPolicyIds`. Do not implement cart arrays, arbitrary client JavaScript, monetary CRUD, authorization in hidden controls, or repeated one-SKU checkout requests as a substitute for atomic splitting. Preserve all account-bound command inspect/retry/acknowledge controls. Follow the generated configuration instructions and report the selected edition and its simulation/bookkeeping limits.
