# Working single-SKU shop applications

For a request for an exportable shop, product ordering, or “电商、下单、库存”, use `create_single_sku_shop_app` before visual styling. It reuses the editor's reviewed NestJS starter for public products, OIDC login, buyer-owned orders, role-gated catalog management, atomic stock reservation/cancellation/restocking, and idempotent retry. Each order contains one SKU with quantity 1–99 and a server-calculated amount in integer minor units. Product deletion, absolute stock replacement, payments, carts, shipping, tax, refunds and a multi-merchant marketplace are not included; describe that boundary accurately.

Use `authentication: "local-keycloak"` only when the user chose the local OpenPencil Keycloak setup. Otherwise use `authentication: "oidc"` with the user's public `issuer` and `client_id`; ask for missing public configuration and never invent it or request credentials. Choose `locale: "zh-CN"` for Chinese page copy or `"en"` for English. If the reviewed NestJS Provider is unavailable, ask the user to enable it in Settings → Plugins. Never bypass provider authority using eval or hand-written plugin data. Existing Backend/authentication flows are preserved; use an empty document for this starter instead of overwriting them. Older template documents are not upgraded automatically. Recreate in a new document or explicitly migrate the model, commands, pages and database, including historical `product_title` and `created_at` values; do not silently replace existing declarations or unresolved saved attempts.

After creation, call `switch_page` with `shopPageId`, inspect all returned `exportPageIds`, and style the existing nodes. Preserve real controls, document and page state, attempt-key states, bindings, events, data sources, command declarations, routes and authentication. Keep browser recovery enabled for checkout, cancellation and restocking. Preserve inspect, saved-request retry, and explicit acknowledgement actions. Do not clear attempt-key state directly; acknowledge the exact saved key only after the user confirms the result was checked. Recovery retry uses the stored payload, never newly evaluated form fields. Do not replace working pages with static product cards, invent client-side inventory writes, or grant buyers unrestricted inventory CRUD. All returned pages must be exported together using React or Vue source export.

Keep title search, fixed ascending price order, sold-out labels and the selection guard. Preserve the selected product's unit price, displayed stock and estimated total in integer minor units, with integer quantity validation from 1–99 and no greater than displayed stock. Keep explicit confirmations before placing or cancelling an order. Checkout parameters remain `{ skuId, quantity }`; never submit a client-calculated price or stock update. Current availability and final pricing are confirmed by the server. Preserve newest-first orders, server `product_title` snapshots and `created_at` timestamps, localized status labels and cancellation-success feedback.

On the manager page, preserve search and pagination across all products, including inactive ones. Creation validates a non-whitespace title of at most 16,384 characters and nonnegative signed 32-bit integer prices and initial stock (0–2,147,483,647); these UI checks are not database `CHECK` constraints. Product edits send only `title`, `price` and `active`, never `stock`. Metadata saves overwrite the submitted fields without comparing versions across managers; do not claim conflict detection. Stock additions must use the verified-role-only `restock-product` command with `{ skuId, quantity }` and integer quantity 1–100,000, checked server addition under a row lock, a required attempt key and browser recovery. Do not recreate stock addition as a read-then-write resource update. When explicitly upgrading an older template, remove `stock` from product `updateFields` as well as adding the command and its recovery UI; page changes alone do not restrict the old API.

Creation and metadata saves are ordinary resource CRUD, without the command's idempotency ledger or persistent browser request recovery. Among manager writes, only restocking has that recovery. If a creation response is lost, query the product list and check the result before deciding to retry; a second create can produce a duplicate. Never describe all catalog writes as exactly-once operations.

Report the generated routes and the source-export step. The tool only changes the document; it does not start services, create database products, grant catalog-manager roles, deploy or prove real login/persistence. Follow the exported README for service configuration, configure the manager's verified role in the identity service, and use the catalog page to manage product details and stock additions. The device stores bounded attempt keys and request parameters without tokens or full results. After refresh, sign in again with the same account, inspect the saved attempt, then explicitly retry its original request. Nothing is automatically resent. Users must check My orders and acknowledge the saved attempt before starting another order; a changed command version cannot be retried blindly. For restocking, current stock alone cannot prove whether an attempt committed: resolve its saved-key request before acknowledging it and starting another addition.
